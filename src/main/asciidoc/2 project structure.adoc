= Project Structure

A typical Grails Plugin Collective (GPC) project repository is organized in a way that makes it easy for contributors and users to find code, documentation, and supporting resources.

== Repository Layout

A standard plugin project (created with `grails create-plugin my-plugin`) will contain the following:

[source]
----
my-plugin/
 ├─ gradle/                     # Gradle artefacts and additional build files
 ├─ grails-app/                 # Grails resources (domain, services, controllers etc)
 |                              # Leave out empty folders (aka remove .gitkeep)
 ├─ src/
 |  ├─ main/groovy/             # Plugin source code
 |  ├─ test/groovy/             # Unit and integration tests
 |  └─ integration-test/groovy/ # Unit and integration tests
 ├─ README.adoc|md              # Overview and usage instructions
 ├─ LICENSE.md                  # Open source license
 ├─ build.gradle                # Gradle build configuration
 ├─ gradle.properties           # Gradle project configuration
 └─ settings.gradle             # Gradle project settings
----

Extras, not created automatically:

* `src/main/asciidoc/` — Documentation written in AsciiDoc format
* `CONTRIBUTING.adoc` — Guidelines for contributing to the project
* `.github/` — GitHub Actions workflows for CI/CD and releases and the release-drafter GH plugin

Keeping this structure consistent helps contributors quickly orient themselves in any GPC project.

You can copy the files from this project to your own gpc project.

== Recommendations

These recommendations follow the same practices of Grails plugins maintained by the Grails core team.

=== Dependencies

Efforts have been made to keep GPC plugins lightweight by minimizing dependencies.

* Start with the default `build.gradle` generated by `grails create-plugin`
* Replace standard Grails dependencies with a minimal set, for example:

[source,groovy]
.build.gradle
----
include::{project}/build.gradle[tag=dependencies]
----

* If your plugin relies on dependencies that *must* be exposed to plugin users, apply the `java-library` plugin and declare them with `api` instead of `implementation`.

.Example
[source,groovy]
----
// Bad: exposes too much and bloats user’s dependency graph
implementation "org.grails:grails-core"

// Good: keeps the plugin lean, only exposing what’s necessary
api "org.apache.grails:grails-micronaut"
----

This approach ensures plugins stay modular, compatible, and easy to integrate.

=== Recommended Licenses

For maximum compatibility with Grails (licensed under Apache 2.0), GPC projects are encouraged to use a permissive license:

* Apache License 2.0, recommended for most cases, and 100% compatible with Grails Core.
Just copy the `LICENSE` file from this project.
* MIT License
* BSD 2-Clause or 3-Clause

These licenses encourage broad adoption, contributions, and commercial use.

Avoid strong copyleft licenses (e.g., GPL), as they restrict usage in many commercial projects and may limit adoption.

== Summary

* Maintain a clean, predictable repository layout
* Keep dependencies minimal and use `api` only when necessary
* Prefer permissive licenses such as Apache 2.0 to align with Grails and encourage adoption
* Provide clear documentation (`README`, `CONTRIBUTING`, `src/main/asciidoc/`)

Consistency across projects makes it easier for contributors to collaborate and ensures long-term sustainability of the Grails Plugin Collective ecosystem.
